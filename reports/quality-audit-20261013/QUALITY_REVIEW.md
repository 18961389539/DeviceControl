# DeviceControl V2.0 RC：按 12 项质量标准全面复审

审查日期：2026-10-13（Asia/Shanghai）。基线提交：`ed1aa9f1a5f41bc0d18be5e340d2672facbda45c`。本次检查已整改后的代码，不直接沿用 10 月 12 日报告结论。评价依据是用户提供的 12 个核心特性与 L1～L5 自定义成熟度模型，不是行业认证。

**结论：正常功能和工程基础已有明显改善，但仍有 4 项 P1 恢复/门禁缺陷，尚不能认定整体达到 L2，更未达到 L3 现场可靠门槛。继续保持 RC / Simulation，正式放行结论为 NO。**

最关键的问题是恢复闭环：正常启动后的恢复要求现在能跨重启保留，但在启动再次中断、恢复状态写入失败和并发门禁更新时仍可能失效；未解决部署会连用于解决它的回滚接口一起阻断。功能回归通过不能证明这些边界正确。

本次仅新增审查报告、隔离复现程序、测试日志和浏览器测试截图，没有修改产品源码、现有工站配置或运行数据。测试使用随机端口和临时数据目录。项目没有真实 PLC、相机、运动控制驱动，本次不把软件仿真结果解释为实机可靠性或安全验证。

## 4. 可执行问题清单

P1：影响恢复门禁、状态可信或必要恢复能力，应在下一次正式放行前解决。P2：诊断、稳定性、可用性或验证缺陷。当前仿真范围未认定 P0。以下共 **4 项 P1、5 项 P2**；另有 3 类工程能力缺口，不把能力缺口伪装成已复现故障。

### N01 · P1 · 中断部署无法通过现有回滚接口解除

位置：`StationUpgradeManager.cs:291`、`:299`；`DeviceRuntime.cs:366`、`:374`；`Governance.cs:227`；`DeviceRuntime.cs:89`。

Rollback 接受 Interrupted / ManualRecoveryRequired，但首先进入 WithConfigurationChange，后者查询当前未解决部署并直接拒绝。回滚内部的配方和流程回滚也会再次进入相同门禁。提示要求“先人工检查并回滚”，实际回滚路径不可达。

隔离复现：InProgress 在启动转换为 Interrupted；Auto 被拦住（正确），Rollback 同时被拦住，部署一直保持 Interrupted。这个复现使用基线相同记录，证明甚至无需修改任何版本也无法解除；没有冒充完整半写断电演练。

修复：为特定部署建立受控恢复资格，而非删除全局门禁。核对站点空闲/手动、当前版本、备份、操作者和恢复目标后，允许该恢复事务处理自己拥有的阻断；其他未解决记录仍须阻断。嵌套配方/流程操作必须遵循同一恢复上下文。

验收：在 Flow / Recipe / 最终日志提交各边界中断；普通启动与发布持续拒绝；授权恢复能完成、留下证据并解除门禁；其他部署、新版本冲突和恢复失败不能被绕过。

### N02 · P1 · 启动恢复消费标记与建立恢复要求不在同一事务

位置：`SqliteStore.cs:161`、`:187`、`:188`；`RunJournal.cs:24`；`DeviceRuntime.cs:57`、`:60`。

RecoverInterruptedCycles 提交 Interrupted 并删除 run_inflight；直到后续 DeviceRuntime 构造才写 recovery_state。两者之间进程再次退出，下一次启动无法得知仍需要人工确认。

已复现：仅构造一次 RunJournal，模拟停止在事务已提交/Runtime 尚未创建的边界；下一次 journal 的 recoveryCount=0、runtime.recoveryRequired=false，数据库仍有 Interrupted。正常完整启动三次均 true 的旧修复依然成立，缺口是边界原子性。

修复：同一 SQLite 事务内写 Interrupted、置未解决恢复要求、清 inflight；Runtime 只读取已提交恢复状态。不要以任意历史失败永久封锁站点。

验收：在恢复事务前/中/后和 Runtime 创建前注入退出，连续重启仍必须保留恢复要求；明确确认后才解除。

### N03 · P1 · 恢复状态拒写被吞掉，重启后故障门禁丢失

位置：`DeviceRuntime.cs:184`、`:446`、`:450`；`RunJournal.cs:53`；`SqliteStore.cs:365`。

EnterRecoveryRequired 先置内存 true，写数据库失败仅记日志。手动动作没有持久动作意图，后续重启不会从 inflight 恢复这类未解决故障。

已复现：隔离 SQLite INSERT 触发器拒绝 recovery_state，注入 XStuck 并回零失败，重启前 recovery=true、重启后 false。这是确定性拒写，不声称模拟了所有磁盘满或断电行为。

修复：动作执行前持久化意图；意图不可写则拒绝开始。故障状态与动作结果原子提交，写失败保留未解决意图，启动进入人工核查。不能以“尽力写一条日志”作为恢复可信依据。

验收：手动动作、停止、周期结束、确认恢复分别注入拒写/锁超时；进程重启后恢复门禁不能因存储恢复可写而消失。

### N04 · P2 · 超时仅覆盖响应头，部署工作室仍无统一超时

位置：`frontend/app.js:7`、`:12`、`:21`、`:127`；`station-console.js:70`；`station-template-studio.js:31`；`station-upgrade-studio.js:30`；`fleet-rollout-studio.js:141`；`deployment-sandbox-ui.js:21`。

fetch 在响应头到达时结束，helper 的 finally 清计时器，调用方之后的 res.json 不受截止时间保护。服务器只发送头和部分正文时，polling/inFlight 可持续不释放。模板、升级、灰度和沙箱还直接 fetch，未接入这套 helper。

已复现：本地 HTTP 发送 JSON 响应头与一个 `{` 后不结束；实际 helper 在 8500ms 后仍未结束正文读取，超过配置 8000ms。

修复：统一客户端覆盖连接、状态检查、正文读取/大小/解析的整个过程。写超时保留“结果未知”，引入持久 commandId 与查询入口，不自动重发动作。新鲜度基于最后一次完整有效快照，不能在任意读请求收到头后即清除。

验收：无响应、只有响应头、截断正文、非法 JSON、令牌过期；主工作区和所有工作室都在约定时间内释放忙状态、明确标过期或未知结果。

### N05 · P1 · 门禁快照 Clear 后逐项更新，并发读能瞬间放行

位置：`StationUpgradeManager.cs:79`、`:97`、`:98`、`:75`。

ConcurrentDictionary 只保证单操作线程安全，不保证 Clear 与逐项填充的整体原子性。另一工站在刷新过程中读到无 key，会把未解决部署解释成无阻断。用无锁读取避免锁序倒置的方向合理，发布快照必须原子。

已复现：反射调用现有 RefreshUnresolved 方法 1000 次，同时读公开 UnresolvedReason；始终存在同一 Interrupted 文件，却出现 23430 次返回 null，最终又恢复阻断。此为并发快照读取证据，不宣称本次已经复现真实硬件动作或完整 HTTP 启动成功；次数随调度变化，不能当事故发生率。

修复：构建完整不可变 dictionary 后通过单次引用替换/Volatile 发布；读者只读同一快照。注册缺失当前也返回 null（`RunEligibility.cs:24`），应区分未就绪与合法无阻断，不能让“未注册”自然等于放行。

验收：A 刷新部署状态、B 有未解决记录时高并发读取和启动，B 始终阻断；同时验证无死锁。

### N06 · P2 · 历史灰度/模板损坏仍可阻止全部 API 启动

位置：`FleetRolloutManager.cs:51`、`:57`；`StationTemplateCatalog.cs:24`；`Program.cs:282`、`:283`。

灰度构造器逐文件直接反序列化，异常传播到 Program 的急切初始化；模板目录也在启动直接解析。动态工站异常隔离的旧修复没有覆盖这些对象。

已复现：独立临时目录中一个 roll-*.json 内容为 `{`，FleetRolloutManager 构造抛 JsonException；结合启动代码可确定 API 在 app.Run 前失败。模板路径本次仅静态确认，未单独注入。

修复：隔离损坏记录，阻断受影响站点/功能，同时保持只读诊断与健康入口；未知归属时可阻断运行，但不应关闭诊断。提供归档/修复流程，保留原始证据，不自动猜测成功。

验收：模板、单站部署、灰度历史、工站配置逐类损坏；诊断入口仍能明确指出文件和影响范围，受影响动作拒绝。

### N07 · P2 · 实际 500 被审计为 200 / Accepted

位置：`Program.cs:59`、`:62`、`:65`；`Governance.cs:102`。

finally 执行时未处理异常尚未由外层服务器变成 500，ctx.Response.StatusCode 仍可能是默认 200。AuditTrail 将所有 <400 状态标为 Accepted，从而制造成功证据。

已用真实隔离 API 复现：发布配方时 SQLite 拒写，客户端 HTTP=500，数据库 audit.http_status=200、Outcome=Accepted。

修复：明确捕获异常，持久化 Failed/异常类型/关联 ID，再统一输出错误响应；响应传输成功、命令受理和业务完成分开记录。审计介质错误也要有明确策略，不能覆盖原始失败或将已执行命令显示为可安全重试。

验收：未处理异常、业务拒绝、取消、写审计失败、已执行但回包失败；审计状态与业务结果一致，且不会记录为 Accepted 后无最终结果。

### N08 · P2 · Windows 发布验收与测试进程清理仍不可靠

位置：`tests/test_recovery_v20.py:47`；`tests/test_api_v14.py:36`；`tests/test_api_v19.py:64`；`.github/workflows/software-check.yml:7`。

本次 V20 测试因符号链接权限失败；V14/V19 的业务断言完成，但清理数据库时 WinError32。脚本直接终止 dotnet run 并等待宿主，不保证其应用子进程/文件锁均释放。现有发布门禁超时杀进程树不能代替每个正常测试结束时的完整清理。本次日志证明残留锁，未据此认定数据库业务损坏。

修复：测试基础设施编译一次后运行 DLL、记录并终止测试所有子进程、确认监听端口关闭和连接释放；符号链接能力预检并给出 BLOCKED，正式要求仍须在有能力的环境执行；CI 加 Windows 矩阵。不要把打印 PASS 或受限测试跳过当发布通过。

### N09 · P2 · 事件落盘仍不足以关联完整故障闭环

位置：`DeviceRuntime.cs:456`、`:464`；`RunJournal.cs:65`、`:67`、`:80`；`Governance.cs:77`、`:115`；`Program.cs:69`。

RunEventEntry 有 RunId，但 runtime.Log 调用 AppendEvent 时不传；没有 nodeId、commandId、TraceId 或异常链。恢复表只保留单份最新状态，审计多为方法/路径，没有输入版本和前后差异。审计 API 仍只从内存最近 2000 条分页。事件日志在运行锁中同步写文件，超过 8MiB 时读取再覆盖，存在调度延迟和非原子轮转风险（未做崩溃注入，不声称已丢日志）。health 只探 A 存储，始终 HTTP200，不表示各工站/恢复状态就绪。

## 5. 工程能力缺口

### G01 · 性能、容量和长期稳定性

`SqliteStore.SaveRecipes` 仍全表删除重插历史配方；历史周期、节点证据、审计、部署 JSON 和备份缺少整体容量与归档策略。会话/计划清理触发于后续登录/预检，不能称独立周期清扫；有效会话与计划数量无明确上限。需建立负载模型和容量预算，不先猜测瓶颈或给出伪造 P99。

建议验收：至少 72h 软件仿真老化，覆盖多工站并发、长流程、周期性故障和日志轮转；报告内存/句柄趋势、CPU/磁盘、任务结果、P95/P99、吞吐、恢复时间。72h 是工程建议，不是认证阈值；响应预算需绑定实际目标节拍。

### G02 · 模块边界、扩展与自动化回归

`Contracts.cs` 已有设备接口，但 Runtime/OrdinaryInterlockMonitor 依赖具体 SimIoController，MultiStationRegistry 手工构建仿真驱动。新增节点同时影响 C# 执行/验证/质量模型与 JS 引擎/编辑器/模拟器。没有足够证据支持“替换相机不触及业务”和“新增算法不改核心调度”。

建议拆分运行资格、命令状态、设备工厂、节点注册/执行契约；建立 C#/JS 契约一致性测试，逐步明确离线模型用途。配置、驱动和节点应有 schema/兼容版本与迁移策略。为 N01～N07 建立正式故障回归，不能长期只依赖审查探针。

### G03 · 易用性、身份与完整交付

UI 已有离开保护，但画布缓存不具备崩溃/浏览器重启恢复；renderRecovery 不呈现新增 eligibilityBlock，可能显示“无需恢复”而 Auto 被拒绝。部署页面保留多代功能区块，需按“预检→部署→证据→恢复”任务组织。README 的旧环境结论、多版本入口和旧发布状态文件缺少统一生成机制。

商业交付还缺正式身份/账号撤销、密钥管理、完整程序版本清单、配置 schema 迁移、Windows 服务安装、离线依赖、升级失败回滚和介质恢复手册。现有配置部署/备份沙箱是有用基础，不能等同程序二进制升级或灾难恢复。

验收：普通用户完成启动/停止/查故障，工程师完成定位/核对/恢复，记录操作次数、误操作与耗时；干净机器安装、升级、失败回滚可重复，程序/配置/流程/算法版本可追溯。

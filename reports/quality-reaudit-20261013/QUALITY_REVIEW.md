# DeviceControl V2.0 RC：修复后按 12 项标准重新审核

审查日期：2026-10-13（Asia/Shanghai）。对象：当前工作区，包含 GPT-6 Luna 的未提交修复以及最后的 500 响应补丁。评价依据：用户提供的 12 个核心特性、五项工业软件重点和 L1～L5 自定义成熟度模型，不是行业认证。

**结论：上一轮针对性整改有实际效果；本轮完整门禁为 46 PASS、0 FAIL、1 BLOCKED。但补充故障注入发现 2 项 P1 和 6 项 P2 问题/工程缺口。整体仍不能认定达到 L2，更没有达到 L3 的现场可靠门槛。维持 RC / Simulation，正式发布不批准。**

决定性证据不是功能数量或界面美观：有效流程在末尾等待期间失去普通工艺条件，仍被记录为 Completed；写操作收到断流或坏 JSON 时，其结果不确定性仍未被准确呈现。另有审计拒写不影响 ready、工站审计归属错误、固定工站配置损坏阻断诊断等问题。

“N01–N09 已完成针对性修复”与“所有异常场景已完成可靠性闭环”是不同结论。本轮确认多项旧缺陷已经修复，同时检查了旧测试未覆盖的邻近边界与跨模块组合。没有因发现新问题否认已有改善，也没有用旧报告代替本次验收。

本轮未修改产品源码、现有配置或工站数据。新增仅为本目录的报告、隔离探针、日志和测试截图。故障注入使用临时根目录、测试数据库和随机 API 端口；CORS 专项使用短暂的独立前端 HTTP 服务，结束后关闭。没有实机控制、长期老化、真实介质断电或商业交付演练。

## 3. 本次问题清单

P1：影响任务结果可信或故障后必要状态核对，应在下一次正式放行前解决。P2：明确的诊断、稳定性、交互或工程恢复缺口。未在软件仿真范围认定P0。

### R02 · P1 · 末尾 Delay 期间普通工艺条件失效仍返回 Completed

位置：`backend/DeviceControl.Api/DeviceRuntime.cs:394`、`:295`；`FlowEngine.cs:240`。

Sequence入口检查普通互锁，但Delay只有Task.Delay；执行结束和周期完成前没有再次确认条件。后面有节点时可能在下一边界拒绝，末尾等待则不存在下一检查。

**真实API复现**：发布合法且通过质量门禁的500ms Delay流程，正常使能/回零/切Auto后启动；80ms时将GuardClosed=false并保持。最终guard=false、outcome=Completed、state=Idle、recoveryRequired=false、完成计数=1。

这与此前相机末尾复核修复不是同一场景。评价的是普通仿真工艺约束及结果准确性，不据此作硬件安全功能结论。

**整改**：明确所有长步骤的条件监控策略，统一发出取消/工艺中断；完成前复核取消、工艺条件及状态，禁止无依据地提交Completed。不能只给相机补特例。

**验收**：末尾Delay、分支Delay、暂停期间门/气压变化、末尾停止请求；输出结果、恢复要求、事件和持久记录应一致。

### R03 · P1 · 断流/坏正文的写结果不确定性没有完整表达

位置：`frontend/api-client.js:10`、`:31`、`:33`；`frontend/app.js:96`、`:115`；`station-upgrade-studio.js:31`。

只有AbortError转换成“结果未知”。服务端收到POST后断开连接、返回截断/非法JSON，则仍抛普通fetch/JSON错误；调用方通常只展示e.message。生成的X-Command-Id局限于helper局部headers，错误对象没有保留commandId。连超时提示也不给出用于核对的具体ID；当前没有按commandId查询完整命令生命周期的专用入口。

**实际helper＋受控HTTP服务器复现**：服务器收到一次POST并模拟写入计数后主动断连接，客户端得到fetch failed；返回坏JSON得到“无效JSON”；两者均未标为未知，error.commandId=null。慢正文超时会正确显示未知，但commandId仍为null。没有观察到helper自动重发，也没有声称真实设备重复动作已发生。

**整改**：不能确认服务端拒绝/完成的网络、正文和解析异常都进入结果未知状态；错误对象与UI保留commandId/traceId及时间、站点、操作；允许按命令查询受理/执行/结果。不要自动重发。是否引入幂等键或对未解决命令阻断后续同类动作，应按具体动作设计。

**验收**：服务端已提交但回包断流、坏JSON、响应过大、超时、500；用户能够用具体ID核对，明确区分业务拒绝和结果未知。

### R01 · P2 · 单站回滚后不能核对续跑旧灰度批次，恢复提示欠明确

位置：`FleetRolloutManager.cs:260`、`:312`；`FlowRevisions.cs:138`；`Governance.cs:246`。

Rollback恢复内容时发布新的流程/配方ID；Reconcile仍要求与批次最初Expected ID完全一致。内容恢复不等于ID恢复，因此发生部分提交的旧批次不能借此回到Pending。

**真实API复现**：批次B部署后模拟中断，重启、单站回滚成功，流程定义/配方值均恢复；两个活动ID为新的回滚版本。Reconcile返回409“工站不在原始版本基线上”。

**重要界限**：V17文档规定严格原始基线、必要时关闭批次。本次已验证Abort=200、重新创建批次=200，且新批次基于已恢复的新ID。因此这不是“所有恢复接口都不可达”或危险放行，不能把它列成已证实P1死锁。

**整改选择**：保留保守策略时，直接说明“内容已恢复、旧批次必须关闭重建”，展示替代步骤；或在明确回滚血缘/内容哈希/当前版本和人工证据下提供受控重基线，不能盲目放宽ID比较。

**验收**：从中断到单站恢复再到批次关闭重建/受控续跑，普通工程师按UI提示能完成，无需猜测409含义。

### R04 · P2 · 审计拒写后命令继续成功，ready仍正常且诊断无此故障

位置：`Program.cs:109`、`:111`、`:121`；`Governance.cs:115`。

审计失败被记录到ASP.NET日志后吞掉，既不持久保留未完成审计意图，也无审计失败计数/健康降级。ready只检查数据库可读，不能证明关键审计写入可用。

**真实API/SQLite复现**：测试触发器拒绝audit_events INSERT。切Manual实际完成并返回200，新增审计行=0，ready返回200/true，diagnostics只显示eventWriteFailures=0，无审计故障。

这是已执行动作与审计故障分离的问题；不应简单在动作完成后返回“失败”诱导重试，也不能以有控制台日志就认为运维闭环完整。

**整改**：定义哪些命令必须先有持久意图/审计容量保证；运行事实与审计状态分别返回。失败至少进入明确降级指标和告警、保留待补记录并有恢复策略；无法保证关键变更可追溯时拒绝新关键变更。

**验收**：动作成功/失败与审计失败组合、锁超时、恢复存储后补录；ready/diagnostics和操作员提示能说明影响，不重复执行原动作。

### R05 · P2 · 工站B的全局部署操作审计被归到A

位置：`SqliteStore.cs:441`；`Program.cs:190`、`:210`；`AuditEntry`只以Path筛站。

全局`/api/upgrades/rollback`及`/api/rollouts/.../advance`的目标在业务参数/记录中，审计却只存HTTP路径。A审计将非stations路径视为A，B审计仅匹配显式B路径。

**真实API复现**：B的单站回滚成功，A审计中有1条全局rollback；B审计查不到该rollback，也没有此次批次advance。全局审计及部署记录仍存在，不能说整个审计行丢失；问题是工站归属/查询链失真。

**整改**：审计结构显式保存StationId、DeploymentId/RolloutId、版本和commandId；批量操作保存目标集或逐站结果，按业务目标查询，不能从路径猜站点。

**验收**：A/B/C、多站批次、全局旧路由、失败回滚；工程师在目标站工作区能查到正确操作，不将B变更误报A变更。

### R06 · P2 · 固定工站B配置损坏仍使全部API启动失败

位置：`MultiStationRegistry.cs:66`、`:70`；`Program.cs:13`、`:342`。

动态工站、模板和灰度损坏已做隔离，但固定B在隔离try外加载；A配置和核心DI初始化同样依赖成功。任一错误仍可能发生于app.Run前。

**隔离启动复现**：只把测试station-B.json改为`{`，A保持正常，进程因JsonException退出，health与diagnostics都不可达。日志明确指出StationConfig.Load→MultiStationRegistry构造。

**整改**：对固定工站应用同样的失败隔离；最小诊断宿主不依赖所有运行模块初始化成功。坏站/未知状态继续阻断动作，不自动修复、删除或猜测配置。

**验收**：固定A/B、动态工站、数据库、模板、部署、灰度逐类损坏；只读诊断可达、错误位置与影响范围明确，受影响动作拒绝。

### R07 · P2 · 过期标志会被HTTP503清除

位置：`frontend/api-client.js:29`、`:35`；`frontend/app.js:221`。

helper在读到可解析JSON后就将dataStale=false，未要求response.ok、数据契约有效或目标是最新运行快照。

**真实helper复现**：读超时后isDataStale=true；随后读一个503 JSON，标志变false。主refresh检查503会锁住连接，因此不能据此声称本次已经复现主界面继续发设备命令；缺陷在于新鲜度契约自身不可信，其他读取也可能清除标志。

**整改**：按数据域/工站记录最后完整有效快照时间，只有成功且契约通过的对应读取更新；失败不能刷新“最新”标志。

**验收**：超时→503、超时→非法结构、跨站读、旧序号响应、并发不同域请求，新鲜度仅由正确的目标快照决定。

### R08 · P2 · 浏览器读不到诊断关联头，UI丢弃错误关联ID

位置：`Program.cs:8`、`:10`、`:42`、`:45`；`api-client.js:12`；`app.js:99`；`station-upgrade-studio.js:31`。

后端CORS允许源和请求头，但没有ExposeHeaders。Node/urllib能读X-Command-Id/X-Trace-Id，正常跨端口Web前端的fetch不能读这些自定义响应头。500 JSON虽有ID，页面错误包装只保留value.error或e.message，提示“使用命令和追踪ID”却未提供具体值。

**真实Chromium复现**：真实前端来源`http://127.0.0.1:5173`请求隔离API，POST模式操作HTTP200；response.headers.get两项均null。该观察验证CORS可见性，不冒充已做完整UI故障可用性测试。

**整改**：显式暴露允许公开的关联响应头；请求helper保留本地生成ID，即使完全无响应也可查询；错误对象、toast/详情/复制诊断入口保留ID。不要只补后台字段。

**验收**：真实前后端不同端口下，成功/500/超时/断流均能从UI取得具体关联依据并查到日志/审计；不可读敏感头仍按策略保留限制。

| 验证结果 | 现有质量模型与回归不覆盖本轮边界，不能仅以模型PASS认定周期真实有效 |

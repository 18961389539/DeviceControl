# DeviceControl V2.0 RC 全面质量复审

审查日期：2026-10-12（Asia/Shanghai）。对象：当前工作区的 C# API、Web 前端、仿真工作流、SQLite 持久化、模板/升级/灰度部署、恢复工具、测试与交付文档。评价依据为用户给定的 12 个核心特性及 L1～L5 自定义成熟度模型，不是认证或正式行业标准。

**结论：主流程具备 L1 的运行能力，并有部分 L2、L3、L4 工程机制；整体尚不满足 L2 的可靠性门槛，更不能认定达到 L3 的现场可靠性。建议保留 RC/Simulation 定位，暂停正式放行，先修复恢复门禁、内存与数据库一致性和版本冲突。**

这不是“功能不够多”的结论。当前的问题是：部分错误路径会使用户看到的版本、恢复要求和可运行状态失去可信依据。正常流程、离线演示与已有回归通过不足以排除这些问题。

审查没有修改产品源码、现有工站数据或原有运行服务。新增内容仅在本报告目录：日志、隔离复现程序、补充 HTTP 测试适配器及截图。测试生成的预览已恢复到审查前内容。未执行实机控制、真实相机/PLC/数据库外部服务、长时间老化或真实断电测试。

### 1.2 对失败结果的区分

1. **环境因素**：初次运行未安装 Python Playwright；本目录隔离安装测试依赖后，四条 Chromium 回归通过。已有 Debug 仿真服务正在运行并占用 DeviceControl.Api.exe，旧 HTTP 测试每次 `dotnet run` 默认重新编译 Debug，因此启动失败；没有停止用户服务。
2. **测试脚本因素**：多个 `Path.read_text()` 不指定 UTF-8，在 Windows 默认 GBK 下失败；若干 `with sqlite3.connect(...)` 只管理事务，没有关闭连接，临时目录清理出现 WinError 32。
3. **产品工具缺陷**：同样的连接生命周期错误出现在正式备份工具 `tools/sqlite_check_backup.py`，导致 Windows 上 `.partial` 不能重命名，这属于产品问题。
4. **契约不一致**：隔离 HTTP 的 V1.0 测试要求 Interrupted 的 snapshots 为 null，当前查询会返回空数组；该脚本仍然失败，必须明确数据契约，不能略过断言。

补充 HTTP 适配器仅将服务启动替换为已编译的 Release DLL，并将服务日志重定向到文件，以避免改写正在运行的 Debug 程序和未消费 PIPE 的阻塞。原断言和 SQLite 清理语义不变。V09/V12/V15 的业务断言完成，但最终清理失败；V10 在 Interrupted 快照契约处失败；V13/V14/V16/V17/V18/V19 全部完整通过。此结果不能替代一次未经适配的完整发布门禁。

### 已有设计值得保留

- 不把取消当完成，不自动重放中断周期。
- 非幂等机构动作不允许自动 Retry；幂等节点自动重试限制为 1～2 次。
- 流程发布先提交 SQLite 再更新内存，并检查工作区基准版本，配方可沿用这个顺序。
- 周期使用固定配方/流程版本；配置发布与周期开始受同一运行锁协调。
- 共享资源原子申请全部 key，取消与释放使用 finally，契约验证 FIFO/超时/取消。
- SQLite 在线备份包含 WAL 已提交页，沙箱检查临时副本，明确不写回运行库。
- 断线时不自动切到另一套浏览器模拟对象；默认绑定 loopback。

## 3. 优先问题清单

P1：在受支持使用场景下影响恢复、结果、版本或交付可靠性，应在下一次正式放行前修复。P2：明确缺陷或工程缺口，应安排治理。没有在仿真范围内认定 P0，也没有把普通仿真互锁当作独立安全系统验证。

### F01 · P1 · 恢复要求没有持久化，重启能够绕过人工确认

**位置**：`backend/DeviceControl.Api/DeviceRuntime.cs:53`、`:248`、`:396`；`RunJournal.cs:22`；`SqliteStore.cs:142`、`:168`。

启动恢复仅通过本次 `RecoverInterruptedCycles()` 返回的数量设置 `_recoveryRequired`。该方法把 run_inflight 转成 Interrupted 后删除标记；没有独立的待恢复状态。第二次启动没有新标记，于是初始化为 false。已停止/失败周期及手动动作故障也主要依赖内存标志，重新启动后同样不会延续要求。

**已复现**：首次启动 recovery=true；未进行恢复确认，再次启动 recovery=false；数据库仍保留 Interrupted。正常停止后，重启也从 true 变 false。轴仍需重新使能/回零，但这些动作完成后即可绕过原本要求的确认，这不能等同于恢复门禁有效。

**修复方向**：持久化工站恢复状态、原因、关联周期/动作、处理阶段、核对人和时间；只有明确确认事务才能清除。不得通过“存在任意历史 Failed 记录”永久封锁；需有独立未解决状态。

**验收**：发生故障/停止/持久化失败后连续重启三次，要求保持；满足清单并确认后重启才解除；记录关联恢复证据。

### F02 · P1 · 配方保存失败使内存活动版本与数据库分裂

**位置**：`Governance.cs:172`、`:182`、`:193`、`:196`、`:213`；`SqliteStore.cs:335`。模板库 `StationTemplateCatalog.cs:101`、`:112`、`:124` 也采用内存先修改、文件随后保存的顺序。

RecipeStore 的 Draft/Validate/Publish/Rollback 先修改 `_revisions`/`_active`，再 Persist。SQLite 事务只能撤销数据库变更，不能撤销已经修改的内存。错误返回后，后续读取和周期可能使用未落盘的版本；重启又回到旧版本。

**已复现**：通过隔离数据库触发器注入写入失败，Publish 抛出 SqliteException；memoryActive 已是新版本、diskActive 仍为原版本，runtimeRecovery=false。触发器用于确定性复现提交失败，不宣称已经执行真实磁盘满试验。

**修复方向**：以候选不可变状态进行持久化，提交成功后一次性替换内存；失败维持原状态。必要时进入持久化故障门禁。模板捕获/发布采用同一原则。

**验收**：对草稿、验证、发布、回滚逐项注入拒写/锁超时/提交失败，断言 API、内存、SQLite 和重启后状态一致。

### F03 · P1 · 配方缺少过期草稿发布冲突校验

**位置**：`Governance.cs:168`、`:185`；对照 `FlowRevisions.cs:113` 的 SourceId 校验。

配方草稿记录 SourceId，但 Publish 不核对它是否仍为当前 `_active`。两名工程师基于同一版本建立草稿，先发布新方案后，另一份过期草稿仍可发布，覆盖后来批准的工艺。

**已复现**：先发布 newer，再发布 older，最终 activeName=older，未提示冲突。

**修复方向**：Draft 和 Publish 支持 expectedActiveVersion/SourceId 双重校验；提供差异与重新基于当前版本创建草稿的流程。显式历史回滚仍使用独立受审计接口。

**验收**：两客户端并发、跨重启、后台升级导致基线变化时，旧草稿必须拒绝发布，现行版本保持。

### F04 · P1 · 中断部署只阻止后续升级，没有隔离工站运行

**位置**：`StationUpgradeManager.cs:43`、`:138`；`MultiStationRegistry.cs:163`；`DeviceRuntime.cs:177`、`:340`。

部署日志被持久化为 Interrupted/ManualRecoveryRequired，但运行启动检查不读取这类未解决状态。一次部署分别发布 Flow 和 Recipe，中途进程退出可能留下部分发布组合。普通流程/配方发布也没有统一的部署恢复门禁。

**已复现**：构造隔离的 InProgress 日志，启动管理器标记 Interrupted；工站完成使能/回零并切换 Auto 后，Start 仍被接受，state=Running。此复现证明门禁缺失，未冒充真实半写断电验证。

**修复方向**：由统一工站运行资格检查纳入未解决部署；阻止自动周期及普通版本变更，保留受控诊断和必要恢复动作；解决日志必须与当前真实版本、备份和核对证据一致。

**验收**：在备份、Flow 发布、Recipe 发布、完成日志落盘四个边界中断；重启后所有启动入口及普通发布入口均阻断，人工恢复后才放行。

### F05 · P1 · 相机采集期间普通工艺条件变化仍可能返回成功

**位置**：`SimHardware.cs:240`；`DeviceRuntime.cs:221`、`:317`。

SimCamera 只在 320ms 延时之前检查普通互锁，结束后仅检查 PartPresent。门状态/气压在采集中变化不会拒绝结果；如果视觉节点位于末尾，后续也不一定再有 Sequence 检查。

**已复现**：开始 LocateAsync，50ms 后将 GuardClosed 置 false，最终 visionOk=true。

**修复方向**：采集结束确认条件仍有效；较长动作期间持续监测或由统一监视器发出取消，状态变化进入明确的工艺中断处理。

**验收**：采集期间变化门/气压/取消信号，不得把不满足条件的结果或整周期标为成功。这里只评价仿真普通工艺约束，不构成硬件安全功能结论。

### F06 · P1 · Windows 备份工具没有关闭 SQLite 连接

**位置**：`tools/sqlite_check_backup.py:38`、`:40`、`:45`。

`with sqlite3.connect()` 退出管理的是事务，连接仍由局部变量持有；随后 `os.replace(partial,dst)` 和异常清理都会在 Windows 上撞到文件锁。

**已复现**：`test_sqlite_reliability.py` 通过真实备份工具触发 WinError 32，`.partial` 重命名失败，finally 删除也失败。C# 在线备份使用 using，没有依据把这个 Python 缺陷扩大为全部后端备份都失败。

**修复方向**：显式 close 或 contextlib.closing，确保释放后再重命名；清理失败不能覆盖原始备份错误，提供明确残留文件诊断。

**验收**：Windows/Linux 均完成健康检查、备份、重命名、只读源保护与失败清理；立即重新打开目标库验证一致性。

### F07 · P2 · 超过 5 万条审计后，启动加载遗漏最新事件

**位置**：`SqliteStore.cs:316`；`Governance.cs:87`、`:89`、`:90`。

查询使用 `ORDER BY time_utc ASC LIMIT 50000`，拿到最早 5 万条；AuditTrail 再仅保留这组记录的最后 2000 条。长运行后的最新操作还在数据库，但重启后无法从现有审计 API 查询到。达到门槛的时间取决于现场写操作量，不能给出未经测量的天数。

**已复现**：插入 50000 条旧记录及 1 条 latest-audit；返回 50000 条，latestEventReturned=false。

**修复方向**：优先直接在数据库分页、按降序加载最新记录，查询支持时间/工站/操作者条件并有稳定排序键。

**验收**：至少 50001 条及百万级数据后重启，最新操作可查询、分页不重不漏；历史档案可访问。

### F08 · P1 · 构建依赖含已知高严重性 SQLite 漏洞

**位置**：`DeviceControl.Api.csproj:9` 的 Microsoft.Data.Sqlite 9.0.10 引入 SQLitePCLRaw.lib.e_sqlite3 2.1.10；构建日志 NU1903。

GitHub 审核公告标识 CVE-2025-6965，涉及旧 SQLite 的内存损坏问题。本次没有证明应用接口可利用，也不把 loopback 服务描述为已遭远程攻击。该依赖风险仍应在商业交付前处理。[公告与受影响信息](https://github.com/advisories/GHSA-2m69-gcr7-jv3q)。

**修复方向**：核实实际 native SQLite 版本，选择包含修复的受支持依赖组合；不要只根据托管 NuGet 版本号猜测 native 库安全。CI 加入依赖审计及高严重性漏洞门禁。

**验收**：记录解析后的完整依赖树、native SQLite 版本；告警消除或有明确评估证据；重新运行数据库/备份/迁移回归。

### F09 · P2 · 前端读写请求没有统一应用超时，数据新鲜度无法保证

**位置**：`frontend/app.js:96`、`:100`、`:127`、`:162`；`station-console.js:60`。

除 health 探测外，多数 fetch 没有 AbortController/应用截止时间。半开连接或服务持续不响应时，refresh 的 polling=true 会阻止下一轮刷新；命令 inFlight 也长期保留。只在 catch 中置 disconnected，意味着浏览器底层超时到来之前，界面可能保留旧状态。控制需要显式的数据过期门禁，不应依赖 fetch 最终抛错。

**修复方向**：统一 API 客户端，读请求有有限超时和新鲜度标记；写请求超时显示“结果未知”，根据 commandId 查询结果后再处理，不自动重发设备动作。

**验收**：服务延迟、网络黑洞、返回非法 JSON、令牌过期；可预测时间内显示状态过期/断开，不把未知写操作宣称失败后盲目重试。

### F10 · P2 · 故障诊断证据不完整，审计写入与动作结果分离

**位置**：`DeviceRuntime.cs:404`；`RunJournal.cs:67`；`Program.cs:55`、`:58`、`:269`、`:280`；`Governance.cs:73`。

运行事件只保留 160 条内存消息，手动动作日志和异常堆栈不会持续保存；周期错误主要保存 Message，故障分类靠中文字符串匹配。审计在 await next() 后执行且无 finally；未处理异常会跳过审计，审计自身写入失败也可能发生在动作已经完成之后。审计只存方法/路径/状态，部分请求中携带的部署编号、目标版本、修改前后内容不在审计行。

ASP.NET 默认控制台日志仍存在，不能说完全没有日志；不足之处在于没有统一持久化、关联和运维查询链路。当前 health 只返回常量，不证明存储可用、所有工站可运行或部署恢复已解决。

**修复方向**：结构化日志包含工站、runId、nodeId、commandId、TraceId、错误码及异常链；关键命令意图与结果有持久化关联；日志介质故障策略、readiness 与 liveness 含义明确。

**验收**：仅凭导出诊断包能定位模块/节点/输入/版本/错误链；控制异常与日志写入异常都有证据，不因返回 HTTP 200 就声称业务执行已完成。

### F11 · P2 · 严格门禁和测试跨平台可信度不足

**位置**：`tools/release_gate_v20.py:78`、`:138`；`tests/test_api_v09.py:21`；`tests/test_api_v10.py:84`；多条 Python 静态/SQLite 测试。

存在默认编码、SQLite 连接未关闭、API 启动依赖 Debug 重新编译、stdout PIPE 不消费，以及 Interrupted null/空数组契约不一致。门禁超时机制只有直接子进程级处理，不能保证服务进程树都退出。progress.json 只在离线任务循环写入，后面的 .NET/HTTP 阶段不更新，运行期间不显示这些阶段的新证据。

**修复方向**：测试显式 UTF-8；关闭全部连接；预先构建隔离产物，HTTP 测试启动专用端口与专用根目录；采集服务日志并清理所有测试子进程；统一 Interrupted 快照契约，增加 available/unavailable 语义；每阶段更新进度。

**验收**：Windows/Linux 两套未适配严格门禁全部通过，失败/超时不残留进程，重复执行不干扰已运行的用户服务；日志可解释每个失败。

### F12 · P2 · 性能和长期资源上限尚无可靠依据

**位置**：`DeviceRuntime.cs:62`；`SqliteStore.cs:280`、`:335`；`frontend/app.js:435`；`Governance.cs:12`；`StationUpgradeManager.cs:30`、`:163`。

300ms 快照刷新包含完整近期周期历史；运行记录还携带节点变量快照。随着流程与历史增加，反复序列化和传输成本上升。SaveRecipes 每次删除并重插所有历史配方，历史越长写入越重。登录会话只在令牌被访问时清理过期项，预检计划仅在 Apply 时移除；大量未使用登录/预检会持续增长。SQLite、部署 JSON 和备份缺少明确保留/归档策略。

这些是源码可见的容量风险，**没有据此编造内存泄漏率、CPU 数值或 P99**。

**修复方向**：轻量运行快照与按需历史分离，数据库分页/增量变更，过期缓存定时清理、容量上限、归档和磁盘容量监控；按工艺节拍定义预算。

**验收**：至少三种规模（1/2/12 工站）及历史增长条件下测 P95/P99、吞吐、CPU、内存、IO、共享资源等待；老化过程中资源有界且结果一致。

### F13 · P2 · 单个损坏工站/部署记录可能阻断整个服务启动

**位置**：`Program.cs:264`；`MultiStationRegistry.cs:71`；`StationUpgradeManager.cs:43`；`FleetRolloutManager.cs:51`；`StationTemplateCatalog.cs:29`。

启动急切加载全部工站、模板、部署和灰度 JSON，反序列化/状态异常直接抛出；某个历史 JSON 损坏可能使健康接口也无法提供。拒绝在不可信状态下执行是正确方向，但当前缺少只读诊断入口和受控隔离方式。

**修复方向**：受影响工站 fail closed，保留故障原因并允许维护诊断；明确必须全局阻断的共享配置错误；不要用“忽略坏文件”来假装恢复。

**验收**：损坏指定历史文件/单站数据库，相关站禁止运行，诊断可访问；未受影响工站按明确定义的隔离策略处理。

### F14 · P2 · 工作区与商业交付流程尚不完整

**位置**：`frontend/flow-editor.js:29`、`:128`；`frontend/index.html`；`README.md`；`tests/fixtures/DeviceControl_V1.9_Preview.html`。

流程编辑切站缓存只在内存；刷新/关闭页面没有未保存退出保护，也没有当前 C# 工作区的草稿自动恢复。版本切换已有 confirm，值得保留，但 reset 操作仍能直接丢弃修改。部署页同时保留 ①～⑨ 多代功能，截图中技术码和 BLOCKED 直接面向用户；可理解性需要任务测试，而不能仅凭美观判定。

生成脚本会把既有 V1.9 fixture 的旧 V1.8 提示更新成 V2.0 提示，说明源前端与交付预览在审查前未完全同步。README 又混合多代入口和旧“缺 SDK”结论。现有“升级/回滚”主要针对流程与配方，不是应用二进制、安装服务、依赖和 schema 的完整升级/回滚产品。

**修复方向**：未保存离开保护与隔离草稿恢复；任务导向部署导航、可读错误说明和诊断详情分层；唯一版本入口及发布时自动生成产物；离线包、配置迁移、服务安装、升级失败处理及备份恢复手册。

**验收**：普通操作员无培训完成启动/停止/查看故障；工程师完成定位/恢复；在干净 Windows 环境安装、升级、失败回滚演练可重复。既有样式和 1440×980 截图仅是视觉证据，不代替易用性验证。

## 5. 故障闭环审查

## 6. 成熟度判断与交付边界

| 等级 | 判断 | 理由 |
| --- | --- | --- |
| L1 能够运行 | 在已测仿真范围内具备 | 真实编译、契约、部分 HTTP/浏览器主路径成立 |
| L2 稳定可用 | 尚未验收通过 | F01/F02/F03/F04/F05/F06，长时间资源/数据可靠性证据缺失 |
| L3 现场可靠 | 未达到 | 故障恢复跨重启失效，诊断与运行隔离未闭环，无实机现场证据 |
| L4 工程成熟 | 部分能力已建立，整体未达到 | CI/测试/版本治理具备，但完整门禁失败、应用升级回滚缺失 |
| L5 产品成熟 | 未达到 | 交付、维护、扩展契约、身份体系和长期维护流程尚未完整 |

不能把“有 CI、灰度发布、沙箱恢复”直接相加得到 L4。这些工程特性必须保证低一级的可靠性门槛。当前仅适合作为本地受控软件仿真/开发验证基线，不能因离线页面功能丰富就认定现场长期使用合格。

## 7. 修复优先顺序

1. **先保证状态可信**：F01/F02/F04，一套持久恢复状态与统一工站运行资格门禁；提交成功后更新内存。
2. **保证动作与工艺版本正确**：F03/F05，配方冲突控制和采集中条件变化处理。
3. **恢复工具与依赖放行**：F06/F08，Windows 备份工具与 native SQLite 风险治理。
4. **把故障讲清楚且记录下来**：F07/F09/F10，最新审计、统一 API 客户端、结构化诊断与结果未知处理。
5. **形成可重复交付证据**：F11～F14，Windows/Linux 门禁、老化性能、故障隔离、部署手册与产物版本一致性。

建议每个修复 PR 包含：触发条件、行为前后差异、对应复现用例、迁移或兼容影响、验收日志。当前审查复现程序是观察工具，尚未转换成“期待正确行为”的正式回归测试；修复时应转换断言并纳入发布门禁。

## 8. 量化验收计划

以下是下一阶段建议的验收方法，不是本次已测成绩，也不是所有工业软件通用的数值标准。

| 维度 | 测量与场景 | 放行原则 |
| --- | --- | --- |
| 正确性/一致性 | 版本竞争、并发命令、部分提交、部署边界中断、连续重启 | 不出现未授权的版本覆盖；内存/持久版本一致；结果状态有依据 |
| 稳定性 | 分阶段做 8h→24h→72h 仿真老化，多站、共享资源等待、交替故障 | 无未知崩溃或持续资源增长；异常都有归因；这几档时长是建议 |
| 性能 | 主页面/诊断 API P50/P95/P99，CPU/RSS/磁盘、周期吞吐、资源等待 | 根据工艺节拍和数据规模设预算，不统一规定 100ms |
| 恢复 | 中断、锁超时、磁盘满、坏库、损坏 JSON、错误版本、三次重启 | 恢复门禁保持；有明确核对和退出条件；恢复不丢失关键证据 |
| 数据 | 在线备份、完整性检查、不同介质上的隔离恢复、WAL/进程终止 | 校验与版本基线一致；恢复演练真实完成，定义可接受 RPO/RTO |
| 测试 | Windows/Linux 原始严格门禁，C# 运行路径与提交失败断言 | 全部必须项通过；不把 skipped/static/model 当作实机或 C# 运行证据 |
| 易用性 | 代表性用户做启动、故障定位、回零恢复、草稿冲突、升级回滚任务 | 记录操作次数、误操作率、完成时间与提示理解情况，制定业务阈值 |
| 维护/交付 | 新节点/新驱动修改范围、诊断所需时间、干净机器升级/回滚 | 能独立交付和定位，无须依赖原作者现场解释 |

**本次发布判断仍为 NO。** 根本阻断不仅是初始环境导致的门禁失败，更包括隔离复现确认的产品行为问题。完成 P1 修复、原始完整门禁和数据恢复验证后，再评估软件 Simulation 的 L2/L3；真实工业应用还需要设备状态核对、硬件适配与独立安全设计验证。

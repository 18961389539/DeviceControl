## 3. 本次新增问题

严重度按本项目软件仿真范围评估：P1为影响关键记录可靠性，应在下一次发布放行前解决；P2为稳定、诊断、运行政策或工程交付缺口。本次未认定P0，也没有将仿真观察描述成实机事故。

### Q01 · P1 · 待补审计溢出后，仍在磁盘的旧记录也被永久丢弃

位置：`backend/DeviceControl.Api/Governance.cs:185`、`:203`、`:208`。

新增失败审计使`_pending`超过10000后删除最早的内存条目；恢复只回放剩余内存条目，随后删除整个`audit-pending.jsonl`，没有确认文件中其他行已提交。内存有界策略因此破坏持久队列的可靠性。

**复现**：隔离数据目录预置10000条合法待补记录，SQLite触发器拒绝审计INSERT；重启后的登录新增一条失败记录；解除触发器再执行写操作。最终只补录9999条原记录，`probe-00000`不存在，spool已删除，健康显示degraded=false/pending=0。

**影响**：已写到补录文件的操作记录仍可能永久丢失，且恢复完成状态掩盖遗漏。

**整改**：持久队列以磁盘记录和提交确认游标为准；内存缓存溢出不能删除未确认事实。分批幂等补录，成功确认后再截断/轮转，明确损坏和容量满的处置。

**验收**：10000/10001及更高负载、补录中途退出、部分INSERT失败、文件轮转失败；所有接受的记录ID最终准确出现一次，未补齐保持降级，健康不能提前恢复。

### Q02 · P1 · 审计与补录同时拒写时，仅保存在内存，重启抹去故障和记录

位置：`Governance.cs:212`、`:215`、`:192`、`:243`。

`TrySpool`吞掉文件写入错误，仅依赖内存列表；命令查询合并SQLite与`_items`，没有合并`_pending`；健康状态取决于当前待补数量，不能保留跨重启的记录丢失事实。

**复现**：SQLite触发器拒绝审计写入，同时把隔离`audit-pending.jsonl`路径设为目录，确定性模拟补录通道不可写。注销实际成功HTTP200；再次登录后审计pending=2，但按注销命令ID查为found=false。关闭服务、恢复数据库写入并重启，记录仍查不到，ready=true。

该观察验证“文件通道不可写”，不是声称已做真实磁盘满测试。注销本身没有设备运行事件作为替代证据，便于严格证明审计事实丢失。

**整改**：分别记录数据库、spool、容量和持久性健康；为必须可追溯的动作建立前置持久命令意图。无可用持久通道时阻止需要留痕的新变更，并保留适当停止/恢复操作。查询展示待补记录和不确定状态，不能用“未找到”暗示未到达；禁止自动重发。

**验收**：数据库拒写+spool拒写/满、动作完成后回包丢失、重启、容量恢复；用户能核对命令事实，未恢复可靠记录之前不能正常ready。动作结果与审计故障分别呈现，不诱导重复执行。

### Q03 · P2 · 非法动态工站文件名绕过故障隔离，使整个API启动失败

位置：`MultiStationRegistry.cs:120`、`:122`；`Program.cs:426`、`:455`。

工站文件内容在try/catch内，文件名规范化、重复ID/容量校验却在外。Program在`app.Run`前解析整个fleet，任何这些异常都能阻止最小诊断宿主启动。

**复现**：保持A/B正常，在隔离`config/managed-stations`加入内容合法的`bad name.json`。进程退出3762504530，堆栈明确为CanonicalStationId→MultiStationRegistry构造→Program启动；无监听器，health/ready/diagnostics都不可达。

**整改**：把文件名、重复/大小写、数量、目录访问与内容错误纳入隔离，并让最小诊断宿主独立于全fleet启动。失败继续拒绝受影响操作，保留原文件，不能猜测或自动删配置。

**验收**：非法文件名、A/B重名、大小写重名、超容量、目录拒读、合法名坏内容；health与诊断可达、影响范围明确，正常站点能按政策工作。

### Q04 · P2 · 审计降级响应头未暴露给浏览器，主界面降级提示无法工作

位置：`Program.cs:13`、`:93`；`frontend/app.js:118`、`:228`。

前端以`headers.get('X-Audit-Status')==='degraded'`显示审计降级；CORS只暴露command/trace/request三头。

**真实Chromium复现**：来源`http://127.0.0.1:5173`请求随机端口API。审计已降级，原生HTTP头为degraded，浏览器HTTP200但auditStatus=null；command/trace仍可读。因此后端拒绝关键变更的门禁仍在，但主状态栏无法通过该头显示降级。

此外头在请求执行前设置，首次造成审计故障的写响应可仍为ok；unavailable也没有被此布尔判断覆盖。这两点为代码检查，不冒充完整UI故障演练。

**整改/验收**：暴露经过允许的健康头或提供明确健康数据契约；UI区分ok/degraded/unavailable，注明响应前后时点。跨端口浏览器验证首次失败、持续降级、完全不可用、恢复补录后清除；操作者能够从提示进入诊断。

### Q05 · P2 · 暂停不在条件监视范围内，短暂失效恢复后可继续记Completed

位置：`FlowEngine.cs:111`、`:133`、`:238`；`DeviceRuntime.cs:380`。

长步骤监视只包执行函数，不覆盖断点gate。暂停等待时没有持续条件检查或失效锁存；继续后只检查当前条件。

**复现**：合法单Delay流程在第0节点断点暂停；GuardClosed=false保持150ms。快照仍Running、无报警、recoveryRequired=false。把条件恢复true后人工resume，最终Completed。

**界限**：本次有明确人工resume，没有自动恢复或实机运动证据。若产品允许断点期间改变这些条件，应形成明确政策；当前“所有长步骤统一监视”的表述不覆盖暂停，不能认定整个任务异常闭环已完成。

**整改/验收**：在周期生命周期定义暂停、异常等待、资源等待的监视与恢复规则，失效可锁存并要求必要状态核对。验证持续/短暂门和气压变化、暂停/恢复/停止竞态；策略、记录、UI和恢复要求一致。

### Q06 · P2 · 人工异常等待持续持有共享资源，使另一工站超时故障

位置：`FlowEngine.cs:173`、`:189`、`:199`；`DeviceRuntime.cs:167`。

人工错误gate在持有lease的try/catch内部；释放在finally，要等人工决定或停止。等待本身没有截止时间。

**真实HTTP复现**：B执行配置合法的VisionLocate+WaitForOperator，采集过程中PartPresent变false；B进入Paused/error并占有CELL-SHARED。A手动触发视觉等待约2.534秒后409，进入Fault并需恢复。停止B后lease归零。

**界限**：已证实停止能释放，不能称永久死锁；保留某类执行机构资源直到核对可能有合理工艺原因。问题是当前统一持锁等待将另一正常站点拖入机构恢复，而没有明确资源隔离/降级政策。

**整改/验收**：针对已结束的采集与真实未确定设备动作分别定义lease生命周期、持有期限及操作员引导；需要保留时明确显示影响站点。无动作开始的资源争用超时是否需要清除全部轴回零，应按业务原因区分。验证等待、取消、人工重试、停止和跨站队列，不能造成无依据的故障扩散。

### Q07 · P2 · 未执行的浏览器验收可被严格门禁标成PASS

位置：`tests/test_browser_v21.py:16`、`:18`、`:50`；`tools/release_gate_v20.py:94`。

缺Playwright/SDK或5173占用时，该脚本打印UNVERIFIED/SKIP并退出0；门禁只看退出码0即PASS。缺SDK完整release另有阻断，但缺浏览器或端口冲突没有此保证。

**实际证据**：首次门禁日志为`UNVERIFIED R08 Chromium CORS: playwright unavailable`，对应JSON状态却PASS。换环境真实执行后通过，不消除门禁此前分类错误。未声称首次整个门禁获批准；其余4条浏览器缺依赖已经使该次失败。

**整改/验收**：所有任务统一PASS/FAIL/BLOCKED/SKIP的结构化契约，严格release拒绝任何未执行项。验证缺依赖、端口占用、浏览器不可启动、探针未到断言、SDK消失；仅真实完成必要断言的任务可PASS。

### Q08 · P2 · 发布状态与哈希清单不能对应当前源包

位置：`DeviceControl_V2.0_ReleaseStatus.json:4`、`MANIFEST_SHA256.txt:1`、`docs/V20_ACCEPTANCE.md:17`。

当前ReleaseStatus仍写fullReleaseGateExecuted=false、dotnetSdkAvailable=false；验收文档及README历史段落也含旧环境结论。顶层清单196项：76匹配、40路径缺失、80哈希不匹配，包括后端/前端/测试和CI。新增修复文件也不受旧清单覆盖。

**界限**：工作区包含未提交修改，旧发布清单与工作树不同可以是正常开发结果；本次不是发现恶意篡改。问题是源包仍携带旧版交付证据，却缺少明确的生成时间、源修订和验收绑定，工程师不能用顶层清单验收当前修订。

**整改/验收**：先选定交付范围与源修订，再从同一构建生成发布状态、清单、程序/配置/schema/节点版本、实际测试证据，区分历史与当前。干净目录验证清单零缺失/零差异；修改后明确使证据失效，不覆盖历史记录伪造验收。

| 可诊断 | 有日志、关联ID、查询、ready | 审计失效和丢失必须可见；最小诊断不随fleet退出 |
| 状态一致与恢复 | Interrupted与恢复门禁已改善，灰度关闭重建路径明确 | 持久审计补录、命令事实查询、暂停失效锁存；不盲目重发 |
| 模块化低耦合 | 模块分离与契约测试具备基础 | 分离命令事实/审计/健康，统一错误代码，减少双模型与路由规则复制 |
| 版本与变更管理 | 配方/流程历史、部署备份、基线冲突可查 | 绑定源包/二进制/配置/schema/节点和驱动版本，完善迁移与交付证据 |

故障闭环逐步评价：**发现异常**有运行与审计故障检测，但暂停缺漏、spool失败静默；**定位原因**后台堆栈可用，但跨端口提示与最小宿主不足；**安全处理**仿真输出清理/取消已有基础，持锁等待隔离不足；**恢复运行**已有人工确认/受控回滚，丢失审计不能恢复；**验证结果**回归较丰富，但存在假PASS且未覆盖本次边界；**保留记录**运行与版本持久化可用，审计仍有确定性丢失。

## 5. 性能、容量、维护与扩展的工程缺口

短时样本：A/B双站已停止执行，8个HTTP客户端共160次快照，160次200；P95 **4.10ms**、P99 **4.57ms**、最大5.49ms，样本吞吐2050.5请求/秒。本机loopback、无大历史、无真实采集/算法/PLC负载，不能作为生产性能承诺，不能据此认定满足设备节拍。

代码检查仍见：`SqliteStore.SaveRecipes:621`每次全量DELETE/INSERT版本集；`RunJournal.EventsForCommand:96`扫描事件文件，事件轮转仅保留尾部；周期、版本、备份与审计spool缺少完整容量预算/保留策略；`AuditTrail`构造会读入待补文件所有行，写入处的10000上限不约束启动加载。负载扩大后的延迟、内存与磁盘影响尚未量化。

`SqliteStore`先插入v1～v5版本记录，再按列逐步迁移，没有完整失败原子性及拒绝未知更高schema的契约证明。恢复缺列有一定幂等性，但仍需迁移中断、新程序到旧程序回滚及备份副本兼容实测，不能以v5现有迁移测试替代完整升级政策。

维护方面，异常代码由中文message匹配，路径同时承担权限、工站和审计推断；C#/JS业务模型并存，质量模型不运行真实Runtime。扩展应优先抽出稳定的节点/驱动契约和组合行为测试，而不是继续增加集中switch分支。当前没有插件热装载、版本依赖/兼容矩阵或驱动替换验收。

## 6. 成熟度与量化整改验收

| 等级 | 本次结论 |
| --- | --- |
| L1 能运行 | 编译、主流程与多站软件仿真回归已确认 |
| L2 稳定可用 | 已有基础；Q01/Q02记录丢失、Q03启动隔离缺漏和长期验证不足，整体未通过 |
| L3 现场可靠 | 故障发现/诊断/恢复/留痕尚未闭环，且没有现场长期证据，不达标 |
| L4 工程成熟 | 有自动化、模块与版本治理基础，门禁可信度、升级兼容和回滚交付不足 |
| L5 产品成熟 | 普通用户/现场工程师任务、商业身份、交付维护、长期扩展未验收 |

建议按 **Q01/Q02 → Q03/Q04/Q07 → Q05/Q06 → Q08及工程缺口**推进。每项整改加入正式门禁，而不只新增一个孤立探针。

| 维度 | 下一轮可验证指标/出口 |
| --- | --- |
| 审计与数据可靠性 | 故障组合与溢出测试中接受记录无丢失；补录完整，未解决时不能ready |
| 功能与恢复 | 暂停/等待/停止/断流组合下状态、结果、报警、记录一致；每种未知写结果能按ID核对 |
| 稳定性 | 先定义目标站点数/节拍/日志量，再做建议至少72小时仿真老化，记录退出、句柄、内存趋势和磁盘增长；时长是工程建议 |
| 可观测性 | 工程师从UI获取站点、节点、时间、command/trace、原因与恢复步骤；计时记录故障定位时长 |
| 性能 | 实际完整流程、8～12站、历史量及备份并发下测P95/P99、吞吐、内存峰值；目标由设备节拍制定 |

| 可部署性 | 干净机器安装、升级、迁移中断和回滚演练；记录成功率/耗时；交付清单与实际产物一致 |

当前最有价值的下一阶段工作是补齐可靠性、诊断和恢复闭环，并让验收证据可信地对应交付修订。已有功能和测试数量不能替代这些出口条件。
